# Dispatch v1.5 — "Mark Sold" fan-out (design)

Date: 2026-07-31
Status: approved design, pre-implementation

## Goal

When an item sells, one click should reconcile the sale everywhere: record it in
Dispatch **and** take the item down on every channel it was listed on. Today
`markSold` only flips the item's own status and price; the per-channel listing
ledger and the live marketplace apps are left stale, reconciled by hand. The
desk sale on 2026-07-31 (sold on Facebook at $35) exposed this: Dispatch showed
`sold`, but the OfferUp and Craigslist rows still read `active @ $40` and both
posts were still live.

v1.5 turns the existing "Mark sold" form into a **fan-out action** that drives
the OfferUp and Facebook takedowns through the emulator (the same surface v1.3/
v1.4 use), flags Craigslist for manual deletion (no logged-in automation exists),
and keeps the ledger honest throughout.

## Scope decisions (from brainstorming, all user-approved)

1. **Capture the sale channel.** Record which channel the sale closed on, for
   future "which channel converts" analysis. One new column, one dropdown.
2. **Single item-level action, not per-channel buttons.** A sale happens on one
   channel but needs takedown on all; the clean model is one action on the item.
3. **Full fan-out (automated).** OfferUp + Facebook takedowns run on the
   emulator; Craigslist is flagged manual.
4. **Craigslist stays honest via a computed task.** Its ledger row is NOT
   auto-flipped to `ended` (that would claim a takedown that didn't happen).
   Today's Tasks are derived from state, not stored, so this is expressed as a
   new **computed** `manual_takedown` task: any `active` listing row still on a
   `sold` item surfaces as "take this down," and clears when Wil marks it done
   (which ends the row). This generalizes beyond Craigslist — see below.
5. **OfferUp takedown always uses "Sold it somewhere else."** Matching a Dispatch
   record to an actual OfferUp buyer is unreliable, and rating the wrong buyer is
   worse than skipping it. Wil rates a real OfferUp buyer by hand on the rare
   occasion an item sells there.

## Data model

One new column on `items`:

- `sold_channel` — nullable text, enum `offerup | facebook | craigslist | other`.
  Null for pre-v1.5 sold items and items not yet sold.

No other schema change. The `listings` ledger already has `status`
(`active | ended | sold`) and `ended_at`; the fan-out uses the existing
`ended` transition. A Drizzle migration adds the column.

## The action

`markSoldAndTakedown(itemId, soldPrice, soldChannel) → SoldResult`

Runs as an awaited server action returning a result object, exactly like
`dropOfferupPrice` / `relistOnOfferup` today.

```
1. markSoldCore(itemId, soldPrice, soldChannel)
     → items.status = sold, soldPrice, soldChannel, soldAt = now
     (always runs first; the sale is recorded even if every takedown fails)

2. for each listing row on the item WHERE status = 'active':
     offerup    → run markSoldOfferup flow  → on ok: end the row (status=ended, endedAt=now)
     facebook   → run markSoldFacebook flow  → on ok: end the row
     craigslist → leave row active (no automation)

3. return SoldResult = { soldPrice, soldChannel, channels: [{channel, outcome, detail}] }
     outcome ∈ ended | failed | manual | skipped
```

- Channels are independent: a failure on one never blocks another or the
  Dispatch status write.
- Channels with no active listing row are skipped silently (not in the result).
- The action does NOT create any task directly. Any row that ends this pass as
  still-`active` on the now-`sold` item (Craigslist always; OfferUp/Facebook if
  their flow returned `failed`) is picked up by the computed `manual_takedown`
  task below. There is no stored task to write.

## The two emulator flows

Both reuse navigation that already exists and is proven in v1.3/v1.4.

### `markSoldOfferup` — captured and run live 2026-07-31

```
accountTab → publicProfile → listingByTitle(name) → manageOwnItem
  → mark-sold-button
  → ucl.affirm-reject-dialog.affirm.button        ("This can't be undone" confirm)
  → "Who bought it?" screen: tap "Sold it somewhere else" radio → Confirm button
  → dismiss post-sale ASPCA donation modal ("No Thanks" / X close)
```

Verified end state: the item dashboard pill reads `Sold`. Two selectors to add
to `offerupTestIds`:

- the affirm-dialog button (`ucl.affirm-reject-dialog.affirm.button`, content-desc
  "Mark sold"),
- the "Sold it somewhere else" radio row + the `Confirm` button on the
  "Who bought it?" screen.

The ASPCA modal is an upsell shown after confirm; dismiss via its "No Thanks" /
close-X and ignore if absent.

### `markSoldFacebook` — build now, verify next live listing

```
Marketplace → your listings → "Open management menu for <title>" (manageMenuPrefix)
  → "Mark as sold" (facebookSelectors.markSold, already defined)
```

The management-menu nav is the same one the proven FB Edit/Delete flows use. The
`markSold: "Mark as sold"` selector is already in `src/config/facebook.ts`, but
the **tap itself is UNVERIFIED** — same status as FB Renew — because the only FB
listing (the desk) is already sold and can't be re-tested. It is built from the
defined selector and flagged needs-live-verification; the first real FB sale
verifies it. If the tap misses, the per-channel result reports `failed` and Wil
finishes by hand. No auto-`ended` is written unless the flow confirms success.

## Computed `manual_takedown` task

`computeTasks` (`src/lib/tasks.ts`) gains a fifth task type. It currently skips
any item whose status isn't `published`; add a pass that emits, for every
`active` listing row whose item is `sold`:

```
{ type: "manual_takedown"; itemId; itemName; listingId; publisherId; publisherName; listingUrl }
```

The row is already in `inputs.activeListings` (the query filters by listing
status, independent of item status), so no query change is needed — only the new
emit branch. A new task-action `completeTakedown(listingId, itemId)` ends the row
(`status=ended, endedAt=now`), mirroring the existing `endListingForRelist`. When
the row ends, the task disappears on the next compute.

This is honest by construction: the task exists exactly while a sold item has a
live listing somewhere. Craigslist always produces one (by design). OfferUp/
Facebook produce one only when their auto-takedown failed — giving Wil a visible
"finish this by hand" nudge instead of a silent stale row, and covering the
emulator-offline / tap-missed failure modes.

## UI

The existing item-page "Mark sold" section (`src/app/items/[id]/page.tsx`) is the
entry point, extended:

- Add a `Sold on` dropdown (OfferUp / Facebook / Craigslist / Other) next to the
  existing sold-price input.
- On submit, show a confirm step summarizing the fan-out, e.g.:
  *"Records sale at $35 on Facebook. Takes down OfferUp + Facebook on the
  emulator. Flags Craigslist for manual delete. Continue?"*
- After it runs, render the per-channel `SoldResult` inline:
  `✓ OfferUp ended · ✓ Facebook ended · ○ Craigslist — take down manually`, with
  `failed` rows called out so Wil knows to finish them by hand.

`manual` and `failed` rows both leave a live listing on the sold item, so they
also appear in Today's Tasks as `manual_takedown` until resolved — the inline
result is the immediate readout, the task is the durable reminder. The Today's
Tasks dashboard (`TaskSection`) renders the new type with the listing's manage/
deep-link and a "Mark done" button wired to `completeTakedown`.

This matches how Wil already watches the reprice/relist flows execute on the
emulator.

## Error handling — degrade, never block

- The Dispatch status/price/channel write (`markSoldCore`) always runs first and
  succeeds independently of any takedown.
- Each channel takedown is wrapped so its failure produces a `failed` result row,
  never an exception that aborts the others.
- A channel with no active listing row is skipped (absent from the result).
- Craigslist never auto-flips to `ended`; it stays `active` and surfaces as a
  `manual_takedown` task until Wil marks it done.
- If the emulator is offline, OfferUp/Facebook rows come back `failed` with a
  clear detail; the sale is still recorded and each failed row surfaces as a
  `manual_takedown` task.

## Testing

Unit (vitest, mocked flows/db):

- `markSoldCore` sets status=sold, soldPrice, soldChannel, soldAt.
- Fan-out maps active rows → the correct per-channel plan; ended-on-success only.
- OfferUp/Facebook flow failure yields a `failed` row and leaves that ledger row
  `active` (no premature `ended`).
- Craigslist always yields `manual`, never an auto-`ended`.
- Channels with no active row are skipped.
- `computeTasks` emits a `manual_takedown` task for each `active` row on a `sold`
  item (Craigslist by design; a failed OfferUp/Facebook row too), and none once
  the row is `ended`.
- `completeTakedown` ends the target row (status=ended, endedAt set).

Live (Wil-driven, like every prior android flow):

- OfferUp takedown: already proven 2026-07-31.
- Facebook takedown: verify against the next real FB listing; until then it ships
  flagged UNVERIFIED.

## Explicitly not in v1.5

- Buyer-matching / OfferUp buyer rating (deliberately manual, decision 5).
- Craigslist takedown automation (no logged-in management surface; backlog).
- Reddit/Watchuseek takedown (watch channels; not part of the desk-class flow and
  no emulator automation).
- Un-sold / relist-after-sold (a sold item that falls through re-lists via the
  existing status controls).
