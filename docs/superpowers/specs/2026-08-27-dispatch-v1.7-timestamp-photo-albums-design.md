# Dispatch v1.7 — Timestamp photo + two-album [WTS] links (design)

Date: 2026-08-27
Status: approved design pending written review

## Goal

Close the last manual gap in the r/WatchExchange flow: the two imgur links in the
generated `[WTS]` comment. r/WatchExchange **Rule 3** requires the timestamp photo
(handwritten username + current date on paper under the watch) to be **linked
separately** from the listing photos. So a compliant post needs two distinct
links: `[Photos](album) | [Timestamp](separate link)`.

Wil's process (approved): upload all photos to the item, mark his hero as
**primary** and the dated shot as **timestamp**, then one action builds two imgur
albums — timestamp photo in its own, the rest in another — and drops both links
into the generated post.

## Organizing principle: Dispatch code vs Claude playbook

- **Dispatch code** owns the durable state: marking which photo is the timestamp,
  and reading the two album links into the post.
- **The album build is a Claude playbook** (approved), not Dispatch code: imgur
  has no clean headless path (the API needs a Client-ID or OAuth, and Wil's
  account was banned once), but uploading through his logged-in Chrome is proven
  (v1.6 session). So Claude builds the albums on request and writes the links back.

## Scope decisions (from brainstorming, all user-approved)

1. **Do not overload "primary."** Primary = the hero photo, shown first on every
   channel (OfferUp/Facebook lead with it). The timestamp gets its own marker.
2. **Album build is Claude-assisted via Wil's Chrome** — reuses his real session,
   no API keys, resilient to the imgur ban history. Not a self-serve button.
3. **Two links stored as item attributes** (`Photos Album`, `Timestamp`) — no
   extra migration, and they never leak into the spec block (which renders only
   its five fixed fields). The publisher special-cases them for the link line.
4. **Split:** timestamp photo → its own album (`[Timestamp]`); all other photos →
   the Photos album (`[Photos]`). Matches Wil's "one for the timestamp, one for
   the rest."

## Components

### 1. Timestamp photo marker (Dispatch code)

- **Schema:** add `photos.is_timestamp` (integer boolean, default 0). Additive
  migration. At most one per item.
- **Core + action:** `setTimestampPhoto(db, photoId, itemId)` sets that photo's
  flag and clears it on the item's other photos (one-per-item), mirroring
  `setPrimaryPhoto`'s shape in `src/lib/photo-order.ts`. Server action
  `setTimestampPhoto(photoId, itemId)` in `actions.ts` wraps it + revalidates.
- **UI:** `PhotoGrid` gains a **timestamp toggle** (a ⏱ button beside the ⭐
  "Make primary"), title "Mark as timestamp — its own separate link, per
  r/WatchExchange". The marked photo shows a ⏱ badge. Primary and timestamp are
  independent markers on (normally) different photos.

### 2. Publisher reads the two link fields (Dispatch code)

- `reddit-watchexchange.ts` reads `item.attributes["Photos Album"]` and
  `item.attributes["Timestamp"]`. The photos line becomes:
  `[Photos](${a["Photos Album"] ?? "PHOTOS_ALBUM_URL"}) | [Timestamp](${a["Timestamp"] ?? "TIMESTAMP_ALBUM_URL"})`
  — real links when set, current placeholders when not, so the post is usable at
  any stage. No other channel reads these keys.

### 3. Album build (Claude playbook — no Dispatch code)

Documented workflow Claude follows on request:

1. Read the item's photos + `is_timestamp` flags (DB) and the files from
   `data/photos/` (`<itemId>-<uuid>.jpg`).
2. Split: the `is_timestamp` photo → timestamp set; all others → photos set.
3. Upload each set as its own imgur album through Wil's logged-in Chrome
   (`imgur.com/upload` → file input → `file_upload`), grabbing each album's
   `/a/<id>` link. (10 MB per `file_upload` call; batch if a set exceeds it.)
4. Write the two links onto the item's `Photos Album` / `Timestamp` attributes.
5. The Publish tab now shows the `[WTS]` with both real, rule-compliant links.

Guardrails: confirm the timestamp photo actually shows the handwritten
username + current date under the watch (Rule 3) before building — Claude can't
verify handwriting, so it flags this for Wil rather than assuming. If no photo is
marked timestamp, build only the Photos album and leave the Timestamp placeholder.

## Error handling

- No timestamp photo marked → Photos album built from all photos; Timestamp left
  as a placeholder (post still generates, flagged non-compliant until fixed).
- imgur upload fails (ban/limit) → report which set failed; links not written;
  the item keeps its placeholders. No partial/corrupt state.
- `file_upload` 10 MB cap exceeded for a set → split into multiple calls into the
  same album ("Add more images"), or report if the album can't be completed.

## Testing

- **Unit (`photo-order`/actions):** `setTimestampPhoto` sets the flag and clears
  it on the item's other photos (one-per-item); leaves other items untouched;
  independent of `setPrimaryPhoto`.
- **Unit (publisher):** renders real `[Photos]`/`[Timestamp]` links when the
  attributes are set; falls back to both placeholders when unset; one set / one
  unset renders correctly.
- **Migration:** additive `is_timestamp` column applies cleanly; existing photos
  default to 0.
- **Album build:** Claude-driven, verified live (like the v1.6 research playbook).

## Explicitly not in scope

- **Dispatch-native imgur API** — deliberately deferred (fragile; Claude-assisted
  chosen). Revisit only if the manual-in-the-loop step becomes a burden.
- **Auto-detecting which photo is the timestamp** — Wil marks it; no image
  analysis.
- **Writing the imgur links from the app UI** — Claude writes them after building;
  a manual "paste link" field is a possible later convenience, not now.
- **Timestamp freshness enforcement** (Rule 3's 2-week window) — Wil shoots a
  fresh dated photo each cycle; Dispatch doesn't police the date.
